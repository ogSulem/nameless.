## 0. Вердикт в трёх строках

Архитектура **задумана** сильно (Redis-first матчинг, разделение UI-сообщения и чата, safe-обёртки над Telegram API, correlation ID, миграции, non-root Docker).

## 2. P0 — блокеры: бот не работает / риск катастрофы

### 2.1. Мэтчинг падает **всегда**. Ядро бота не работает

**Где:** `app/services/matchmaking.py:210`, `:213` (`MatchResult(..., _temp_partner_id=...)`), dataclass объявлен в `:19-22`.

```python
@dataclass(frozen=True, slots=True)
class MatchResult:
    dialog_id: int
    partner_user_id: int
...
return MatchResult(dialog_id=0, partner_user_id=cand_tg, _temp_partner_id=cand_id)
```

У `dataclass(slots=True)` нет такого поля — `__init__` не принимает лишний kwarg.

**Воспроизведено** (см. Приложение A, вывод):

```
premium=False → EXCEPTION: TypeError MatchResult.__init__() got an unexpected keyword argument '_temp_partner_id'
premium=True  → EXCEPTION: TypeError MatchResult.__init__() got an unexpected keyword argument '_temp_partner_id'
dialogs in db: 0
```

**Что это значит для продакшена:**
- совпадение не создаётся **никогда** — ни обычное, ни Premium;
- исключение ловится `ErrorBoundaryMiddleware` → алерт в админ-чат на каждый поиск;
- в `finally` удаляется `lock:match:<candidate>`, а кандидат уже вынут из очереди Lua-скриптом и обратно **не возвращается** → каждый неудачный поиск **теряет ожидающего пользователя из очереди**;
- пользователь видит вечное «Ищу собеседника...».

**Фикс:** добавить поле в датакласс и передавать его явно.

```python
@dataclass(frozen=True, slots=True)
class MatchResult:
    dialog_id: int
    partner_user_id: int
    partner_db_id: int | None = None
```
+ заменить `_temp_partner_id=` на `partner_db_id=`, а `getattr(partner_info, "_temp_partner_id", None)` на `partner_info.partner_db_id`.
+ на любом исключении при создании диалога — вернуть кандидата в очередь и снять его лок.

**Проверка после фикса:** тот же сценарий должен дать `MatchResult(dialog_id=1, ...)` и запись в `dialogs`/`active_dialogs`.

### 2.2. `pip install -r requirements.txt` сегодня ставит OpenCV 5 → приложение не стартует

**Где:** `requirements.txt:13` (`opencv-python-headless` без версии), `:15` (`mediapipe==0.10.14`), `app/services/ai.py:24`.

`AIService.__init__` вызывает `cv2.CascadeClassifier(...)` на уровне импорта модуля (`_AI_SERVICE = AIService()` в `app/handlers/dialog.py:31`).

**Воспроизведено:**

```
pip install opencv-python-headless            # ставится 5.0.0
python -c "import app.main"
AttributeError: module 'cv2' has no attribute 'CascadeClassifier'
```

```
pip install opencv-python-headless<5           # ставится 4.14.0
python -c "import app.main" → app.main imported OK
```

Плюс второй, независимый конфликт: `mediapipe==0.10.14` тянет **`opencv-contrib-python` 5.0.0.93** — то есть в образе оказываются **две** реализации `cv2` (100 МБ + 82 МБ), и какая из них выиграет — лотерея. А после `mediapipe` импорт `cv2` падает уже с `ImportError: libGL.so.1` (спасает только `libgl1` из Dockerfile).

Побочно: mediapipe притаскивает `jaxlib` (349 МБ), `scipy` (113 МБ), `matplotlib` (35 МБ). Это противоречит заявлению «быстрый».

**Фикс (немедленный):** зафиксировать всё. Минимум:

```
# requirements.txt — точные версии, без двух cv2
opencv-contrib-python==4.10.0.84   # то, что требует mediapipe, но 4.x
numpy==1.26.4
mediapipe==0.10.14
# opencv-python-headless УБРАТЬ
```
Стратегически: `pip-compile`/`uv lock` + CI-джоб «собрать образ и `python -c "import app.main"`». Без этого джоба такие поломки будут повторяться при каждом `docker build`.
Отдельно стоит оценить замену `cv2.CascadeClassifier` (устаревший Haar) и mediapipe на один лёгкий детектор (`cv2.dnn` FaceDetectorYN или insightface-ONNX) — минус ~700 МБ зависимостей.

### 2.3. Кнопка «Оплатить Premium» не работает: инвойс уходит в чат бота

**Где:** `app/handlers/subscription.py:34`, вызов — `:137-142`.

```python
async def premium_menu(call: CallbackQuery, ...):
    await _send_premium_invoice(call.message, settings, redis)   # ← message бота
...
async def _send_premium_invoice(message: Message, ...):
    user_id = int(message.from_user.id)                          # ← id БОТА
```

`call.message` — это сообщение, отправленное ботом. У него `from_user` = сам бот. Дальше:
- `edit_ui(bot, redis, user_id=bot_id, ...)` → `safe_send_message(chat_id=bot_id)` → `Bad Request: chat not found` → исключение → `call.answer()` не вызывается, у пользователя кнопка «висит»;
- в ветке прямого ЮKassa `keys.payment_pending(user_id)` и `metadata={"tg_id": ...}` тоже пишутся на ID бота → «Обновить статус» никогда не найдёт платёж;
- админская «тестовая» цена 1 ₽ (`:107`) считается от ID бота.

**Фикс:** передавать `user_id` явно.

```python
@router.callback_query(F.data == "menu_premium")
async def premium_menu(call: CallbackQuery, settings, session, redis):
    await _send_premium_invoice(call.message, settings, redis, user_id=call.from_user.id)
```
и внутри использовать только переданный `user_id` (никогда `message.from_user`).

### 2.4. Через 12 часов активный диалог превращается в неубиваемый дедлок

**Где:** `app/services/matchmaking.py:109` (`ActiveDialog` в БД), `:251-252` (Redis `ex=12h`), `app/handlers/dialog.py:58-60` (получение dialog_id только из Redis).

Картина:
- факт диалога хранится **в двух местах**: `active_dialogs` в Postgres (навсегда) и `active_dialog:<tg>` в Redis (TTL 12 ч, TTL нигде не продлевается — heartbeat отсутствует);
- через 12 часов (или после `FLUSHDB`/потери Redis) Redis-ключ исчезает, а строка в БД остаётся;
- `relay_messages` больше не видит диалог → сообщения пользователей **молча удаляются** обработчиком cleanup;
- `try_match` видит `ActiveDialog` → возвращает `None` → новый поиск невозможен;
- закончить диалог нельзя: `⏭️`/`🛑` обрабатываются только при наличии Redis-ключа.

Пользователь навсегда в состоянии «не чат и не поиск», без единого сообщения об ошибке. То же самое происходит, если Redis-пайплайн при создании матча упал: диалог закоммичен, кэш не записан (`:246-270`, ошибка только логируется) — оба участника застряли.

**Фикс (минимум):** БД — источник истины, Redis — кеш.
```python
async def _get_dialog_id(redis, session, tg_id) -> int | None:
    v = await redis.get(keys.active_dialog(tg_id))
    if v: 
        await redis.expire(keys.active_dialog(tg_id), 12*3600)  # heartbeat
        return int(v)
    # fallback: поднять из active_dialogs и перезалить в Redis
```
Плюс: фоновый sweeper (раз в 5–10 минут) закрывает `dialogs` старше N часов и чистит `active_dialogs`; команда `/stop` как аварийный выход; запись в Redis **до** коммита или компенсирующая транзакция.

### 2.5. Приватность: все фото пользователей уходят в админ-чат с их личностью

**Где:** `app/handlers/dialog.py:533-543` (+ `caption` собирается на `:503-531`).

```python
target_chat_id = int(getattr(settings, "alerts_chat_id", 0) or 0)
if target_chat_id:
    await safe_send_photo(bot, chat_id=target_chat_id,
                          photo=message.photo[-1].file_id, caption=caption)
```
где `caption` содержит: `ФИО`, `@username`, `ID`, рейтинг, ID диалога, вердикт нейросети.

Это происходит для **каждого** фото в **каждом** диалоге, без жалобы и без согласия. Для продукта, который продаётся как «анонимный чат», это прямое разрушение ключевого обещания и тяжёлый комплаенс-риск (152-ФЗ: биометрия/фото + переписка + отсутствие согласия и срока хранения).

Рядом:
- `ErrorBoundaryMiddleware` (`:69-86`) отправляет в админ-чат **текст упавшего сообщения** — то есть куски личной переписки;
- `ComplaintService` (`:63-109`) выгружает в админ-чат лог диалога и **все фото** диалога;
- нет ни одного механизма удаления: `messages`, `photos`, `file_id` хранятся вечно, TTL/партиционирования/джобы очистки нет. Формулировка «сообщения удаляются, остаются только нужные» кодом **не подтверждается** — удаляется только UI-сообщение бота, а переписка пишется в БД каждым сообщением;
- `username`/`full_name` в модели есть (`models.py:28-29`), но не заполняются — зато админ-дамп дергает `bot.get_chat()` и показывает их.

**Фикс:**
1. Убрать безусловную копию фото в админ-чат. Оставить только по жалобе/по решению модератора.
2. Из любых админ-сообщений убрать ФИО/username — только `tg_id` (он и так есть в системе).
3. Добавить retention-джобу: `messages`/`photos`/`complaints` старше N дней удаляются (для фото — вместе с `file_path`), плюс `DELETE /mydata` по команде пользователя.
4. Написать политику приватности и показать её до первого поиска (сейчас нет ни `/help`, ни согласия — см. §4).

### 2.7. В самом чате нет антифлуда

### 2.8. Админ-команды: авторизация «fail-open»

**Где:** `app/handlers/admin_dump.py:303-311`

```python
if settings.admins_set and message.from_user.id not in settings.admins_set:
    raise SkipHandler
```

Если `ADMINS` пуст (а `.env.example` его не требует валидировать) — **любой участник** чата алертов может выполнить `userfile <id>` и получить всю переписку, фото и данные любого пользователя. Плюс команды обрабатываются и в `@router.channel_post`, и в `@router.message` — то есть в группе с несколькими людьми (поддержка, модераторы, «просто посмотреть») доступ есть у всех.

if not settings.admins_set or message.from_user.id not in settings.admins_set:
    raise SkipHandler

+ падать на старте, если `ADMINS` пуст и `ALERTS_CHAT_ID` задан; + аудит-лог на каждую команду выгрузки.

## Приложение A. Репро поломки мэтчинга

```python
# python: fakeredis[lua] + aiosqlite + aiogram (для моделей не нужен)
import asyncio, sys; sys.path.insert(0, ".")
from datetime import date
import fakeredis.aioredis
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from app.database.models import Base, User, Gender, Dialog
from app.services.matchmaking import MatchmakingService

async def main():
    engine = create_async_engine("sqlite+aiosqlite:///:memory:")
    async with engine.begin() as c:
        await c.run_sync(Base.metadata.create_all)
    S = async_sessionmaker(engine, expire_on_commit=False)
    r = fakeredis.aioredis.FakeRedis(decode_responses=True)
    async with S() as s:
        u1 = User(telegram_id=111, gender=Gender.male,   birth_date=date(1990,1,1), city="Москва", is_banned=False)
        u2 = User(telegram_id=222, gender=Gender.female, birth_date=date(1995,1,1), city="Москва", is_banned=False)
        s.add_all([u1,u2]); await s.commit(); await s.refresh(u1); await s.refresh(u2)
        svc = MatchmakingService(r)
        await svc.enqueue(u2.telegram_id, u2.city, is_premium_queue=False)  # ждёт в очереди
        for premium in (False, True):
            await svc.enqueue(u2.telegram_id, u2.city, is_premium_queue=False)
            try:
                print(premium, await svc.try_match(session=s, user=u1, premium=premium))
            except Exception as e:
                print(premium, "EXCEPTION:", type(e).__name__, e)

asyncio.run(main())
```
